### 2026-08-27 — Entity-Intelligence Write Path (P1.1)
- Requirement ID: P1.1, first item in the P1 sequence recommended in `execution/NEXT.md`'s dependency analysis
- Type: Feature | Security
- Summary: First real bridge from a citizen money-flow report into `suspect_identifiers`. Before writing code, inspected `lib/extract.ts` field-by-field and found only one of its four output fields (the UPI-shaped branch of `debitedInstrument`) safely maps to a suspect identifier — the other three either describe the citizen's own account (writing them would mislabel victims as suspects) or don't correspond to any identifier type at all. Recorded as ADR-005, along with two structural findings: `suspect_identifiers.complaintId` can't represent multiple reporting complaints (fixed with an additive `suspect_identifier_reports` junction table, DB-unique-indexed for idempotency — `suspect_identifiers` itself untouched), and trusting the client-supplied `extractedFields` array for this write (as opposed to the citizen's own review screen, where it's fine) would let a citizen forge a false report against an arbitrary UPI ID — fixed by re-deriving extraction server-side from the narrative inside `submitMoneyReport`'s own transaction. The write path itself is a plain module, not a Server Action — no client-reachable entry point exists for it at all.
- Files/areas affected: `lib/db/schema.ts` (`suspect_identifier_reports`, new relations), `lib/entity-extraction.ts` (new), `app/[locale]/report/money/actions.ts` (wired into the existing transaction), `lib/actions/suspect-check.ts` + `app/api/check-suspect/route.ts` (dynamic `synthetic` field, was hardcoded `true`), `lib/actions/case-management.ts` (Related Entities now queries the junction table), `app/investigator/cases/[publicId]/page.tsx` (provenance display), `components/check-suspect/checker-form.tsx` + `locales/{en,hi}/checkSuspect.json` (per-result source label)

Live E2E via the real `submitMoneyReport` Server Action against local Docker Postgres: entity write + audit log confirmed via direct `psql`, multi-report linking confirmed (reportCount 1→2 across two distinct complaints), DB-enforced idempotency confirmed by directly attempting a duplicate-key insert (rejected by the unique constraint, not just application logic), no-false-extraction confirmed (a bank-name-only narrative writes nothing), checker regression-checked (synthetic seed data still returns `synthetic:true`, new report-derived data returns `synthetic:false`), case-detail provenance display confirmed to never render the raw identifier value. Unauthorized-write/forged-provenance/mass-assignment: verified by code inspection that no client-reachable entry point exists to attempt against (no "use server", no API route, no re-export) — not a live attack test, since there's no endpoint to attack.

### 2026-08-27 — Per-Case Mutation Authorization (P1.3)
- Requirement ID: P1.3, next item in the P1 sequence from `execution/NEXT.md`
- Type: Security
- Summary: Added a single centralized `canMutateCase(investigator, assignedInvestigatorId)` function (ADR-007) and applied it to all four case mutation paths in `lib/actions/case-management.ts`: `changeCaseStatus`, `requestEvidence`, `addCaseNote`, `assignCase`.
